# PCC preview Auth activation attempt — 2026-09-29

Target: Neon project `groundbnb` (`divine-resonance-05443204`), schema-only branch `preview` (`br-plain-grass-b8xotge6`), database `groundbnb`. The client explicitly approved enabling Neon Auth on this target. Production branch `br-small-meadow-b8lh69jr` was not changed.

In the Neon console, the branch selector displayed `preview, project groundbnb`. The Better Auth page showed `Enable Neon Auth`. Clicking it returned `permission denied for database groundbnb`, then returned to the inactive enable button.

Read-only SQL Editor queries on `preview` / `groundbnb` showed `current_user = neondb_owner`, database owner `neondb_owner`, and owner `CREATE = true`. For `neon_service`, `CONNECT = true` and database `CREATE = false` on both `groundbnb` and `neondb`. A schema query returned only `pcc`, owned by `neondb_owner`; no `neon_auth` schema was present. This is evidence of the failed activation, not proof of the provider's internal role selection.

The proposed `GRANT CREATE ON DATABASE groundbnb TO neon_service` was entered in the preview SQL Editor but **not run**. Automatic approval review rejected executing it because the client's Auth enablement approval did not specifically authorize this separate persistent database privilege grant. No indirect retry was made. The grant would let Neon's service role create schemas in this preview database; the effect is confined to this database, but persists until revoked.

At that point, the next step was specific client approval for the preview-only grant. [Neon's enable API](https://api-docs.neon.tech/reference/createneonauth) says it provisions the `neon_auth` schema and can target a named database. The resolution below records the subsequent approved action.

## Resolution in the same session

The client explicitly approved the preview-only `GRANT CREATE ON DATABASE groundbnb TO neon_service`. With branch `preview` and database `groundbnb` selected, the Neon SQL Editor reported `Statement executed successfully`. A subsequent `has_database_privilege('neon_service', 'groundbnb', 'CREATE')` query returned `true`.

Retrying `Enable Neon Auth` on the preview branch opened the active Better Auth Users view, which showed no users. A read-only query on preview `groundbnb` found `neon_auth` with nine ordinary tables and the existing `pcc` schema with two tables. The Auth settings page displayed a branch-specific Auth URL ending `/groundbnb/auth`. A separate read-only visit to the production branch's Auth page still showed `Enable Neon Auth`.

Configuration observed, not changed: email signup on; sign-up verification off; email sign-in on; Google shared-key OAuth listed; shared email sender; localhost allowed; no trusted domains listed. Neon warned that anyone on the web can sign up and restricted signups are not yet supported in this console. Therefore Auth provisioning passes, but preview identity safety and app integration do not. No user was created, no real email was sent, no Auth URL or credential was added to Git/Vercel, and no client write route was opened.
