# M1-01AE — Dormant factor-enrollment writer design

Status: offline candidate prepared; migration 0014 and the server protocol are dormant and unexecuted. This note narrows the begin/verify portion of M1-01AD into a reviewable database contract. It does not amend the frozen source, authorize SQL execution, grant functions, enable a role, provision credentials or keys, expose a route, or claim MFA acceptance. Recovery issuance, reset, pending cancellation, and expiry remain out of scope.

## Authority and source mapping

A Google/password session alone is insufficient.
- Frozen Section 11.15, `ADM-07`: bootstrap identity must be trusted and bound to the provider subject; profile email or browser role is not authority.
- `SYS-11`: these operations stay confined to the pinned synthetic local/preview environments; production and recovery are outside this preparation.
- `docs/tasks/M1-01AD-factor-lifecycle-contract.md`: current proposed lifecycle scope and open decisions. This document resolves only the initial enrollment epoch timing as a design proposal.
- Existing storage: `db/migrations/0009_privileged_factors.sql` defines immutable factor identity/envelope fields, `pending → verified|revoked` transitions, one-live-factor-per-account-and-epoch, accepted TOTP steps, append-only audit, finite timestamps, and deferred epoch/event checks. Every factor insert/non-revoked update must match the account's current epoch. `security_epoch_events` permits `factor_enrollment` and exactly one-step increments.
- Existing service: `db/migrations/0012_factor_service.sql` defines the canonical lock order (managed session, account+identity, epoch, factor, account serialization lock, operation/source rows), an account-wide 5-attempt/15-minute challenge window, and challenge-only operation receipts. `db/migrations/0013_factor_service_principal.sql` restricts the existing challenge functions to the exact branch factor principal. Neither migration supplies enrollment writers or lifecycle receipts.

Stable requirements in view: ACC-08, ADM-01, ADM-06, ADM-07, SYS-11, and LEG-12. This design creates no new requirement and changes no ledger status.

## Proposed epoch and history rule

Advance the security epoch exactly once when a new pending enrollment is durably created. In that same transaction, insert the `factor_enrollment` epoch event and pending factor bound to the new epoch, and append `enrollment_started`. If an account has no epoch row yet, establish the schema's initial epoch `0` before taking the single increment to `1`.

Before advancing, the begin operation must reject **any retained pending or verified factor for the account at any epoch**, not merely one at the current epoch. This prevents an epoch change from abandoning a pending factor or bypassing an active factor. Revoked history remains intact. A retry for the same begin operation resolves its existing receipt; it never creates another factor or advances another epoch.

Verification changes that pending row to verified without another epoch increment. In the same transaction it records the unique accepted TOTP step, the session-bound factor attestation and activity, and `enrollment_verified` audit outcome, consistent with the existing challenge writer and AD contract. The service still performs a fresh post-commit identity/session/epoch/factor read before reporting success. This attestation does not bypass later 12-hour freshness, 30-minute inactivity, or five-minute sensitive-action checks.

No pending row is silently expired, overwritten, deleted, or moved across epochs. This design does not define pending expiry, cancellation, or restart behavior; an existing pending row therefore blocks a new begin until a separately reviewed lifecycle operation exists.

## Fixed private SQL surface proposal

All calls are fixed parameterized calls from the trusted server through the dedicated branch factor principal. No browser body may select account, role, epoch, factor, identity issuer/subject, session, envelope, key ID, outcome, or rate policy. The server derives issuer, verified subject, managed-session ID/expiry, active owner/admin identity, and account from the trusted provider/bootstrap boundary. The browser-provided operation UUID is a closed idempotency key only; it conveys no authority. The dedicated factor principal remains the exact same branch principal; no role membership or ordinary-app grant is added.

1. `groundbnb.read_factor_enrollment_context(text issuer, text subject, text session_id, timestamptz session_expires_at) RETURNS jsonb`
   - Private read resolves the trusted active owner/admin account, current epoch (zero if no row), and whether *any* pending/verified factor exists at any epoch. The server generates a candidate factor UUID and target epoch (`current + 1`) from this snapshot. The result is only a preparation hint; begin rechecks everything under locks.

2. `groundbnb.begin_factor_enrollment(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid expected_account_id, bigint expected_current_epoch, bigint target_epoch, uuid candidate_factor_id, uuid operation_id, bytea request_fingerprint, text envelope_key_id, jsonb encrypted_secret) RETURNS jsonb`
   - `operation_id` is the validated closed UUID supplied by the begin request. `expected_account_id`, expected current epoch, target epoch, and candidate factor UUID are generated from the trusted context read, never from browser authority; the database rederives account/epoch and compares them exactly before writing.
   - The server creates the TOTP seed and encrypted envelope only after it knows the candidate factor UUID and target epoch, because `lib/factor-storage.mjs` binds authenticated encryption to environment, account ID, factor ID, security epoch, and key ID. The database verifies the envelope's existing 0009 JSON shape and exact `envelope_key_id = encrypted_secret->>'keyId'`; it never receives plaintext TOTP seed. A concurrent begin that changes the expected epoch fails closed.
   - In one transaction: lock/revalidate current session and active owner/admin account in 0012/0013 order; lock epoch/account serialization; resolve operation replay; reject any pending/verified factor at any epoch; compare expected account/current epoch and target epoch; advance epoch once; insert the candidate pending factor, lifecycle receipt, and `enrollment_started` audit. This relies on the installed active account/session binding. It does not establish or revalidate durable bootstrap seed-to-subject history; that remains a separate prerequisite.
   - Private SQL returns a closed seven-field acknowledgment `{status, operationId, kind, accountId, factorId, securityEpoch, requestFingerprint}`, with `status` `committed` or `rejected`. It never returns key ID, envelope, seed, URI, identity, session data, or protected content. The offline service returns a narrower client acknowledgment and keeps provisioning material non-enumerable; it exposes the material only after a correctly bound committed acknowledgment and fresh state/session check. The client acknowledgment validator excludes the secret. Status lookup never returns provisioning material. This is candidate handling, not a frozen one-time-QR requirement.

3. `groundbnb.read_pending_factor_for_enrollment(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid begin_operation_id, uuid expected_account_id, uuid expected_factor_id, bigint expected_security_epoch) RETURNS jsonb`
   - Private service-only read used to verify a code after the state-read phase. Resolve the pending factor through its begin receipt and current account/epoch. Expected account/factor/epoch values are server-observed concurrency bindings only; the function rederives and compares them. Recheck current session and owner/admin binding. Return the envelope and binding only to the trusted server for decryption/verification; the API response never contains the envelope.
   - This read is not an authorization result. After asynchronous crypto verification, the atomic writer must revalidate all returned bindings and current time.

4. `groundbnb.record_factor_enrollment_attempt(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid begin_operation_id, uuid operation_id, uuid expected_account_id, uuid expected_factor_id, bigint expected_security_epoch, bytea request_fingerprint, text reason) RETURNS jsonb`
   - Called once for an invalid, stale, replayed, or throttled code candidate; `reason` is selected from the existing closed audit-reason set, never copied from a provider error. Resolve the pending factor/epoch from the begin receipt, revalidate and lock in canonical order, update the existing account-wide attempt window, append the allowed audit outcome, and save a rejected `verify` receipt atomically. The private writer action is `recordEnrollmentAttempt`; its acknowledgment has status `recorded` or `rejected` and the same seven bound fields as the other writers. Replays of the same operation are status-only and do not increment the window again. This function accepts no code or code-derived unkeyed digest.

5. `groundbnb.verify_factor_enrollment(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid begin_operation_id, uuid operation_id, uuid expected_account_id, uuid expected_factor_id, bigint expected_security_epoch, bytea request_fingerprint, bigint matched_step) RETURNS jsonb`
   - `matched_step` is derived by the maintained TOTP verifier from the freshly read envelope and submitted code; it is not accepted from the browser. The database resolves factor and epoch from the begin receipt, locks/revalidates session, identity, account, epoch, factor, and operation rows in canonical order, verifies the factor remains pending at the current epoch, and atomically inserts the unique accepted step, changes pending→verified, appends audit, and creates the verify receipt and session-bound attestation/activity.
   - It must not accept client-selected `factor_id`, `account_id`, `security_epoch`, role, arbitrary callback SQL, caller rate limits, secret, or code. Expected account/factor/epoch values are trusted server observations that SQL rederives and compares. A stale session, changed epoch, revoked identity, replaced factor, replayed step, or exhausted rate window fails closed with no verified state or privileged attestation.
   - On commit, return the same seven-field internal acknowledgment with status `committed`; a correctly bound rejection uses status `rejected`. The server then performs a fresh identity/session/epoch/factor read before returning an enrollment-success response. The client acknowledgment is narrower than the SQL acknowledgment. Before a mutation, invalid state may return unavailable; after a writer is issued, an unverified or stale result is unknown unless a correctly bound rejection is confirmed. No protected content is exposed.

6. `groundbnb.read_factor_enrollment_receipt(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid operation_id, text kind, uuid expected_account_id, uuid expected_factor_id, bigint expected_security_epoch) RETURNS jsonb`
   - Read-only status operation bound to current owner/session and exact operation kind. It compares the caller's server-observed account/factor/epoch bindings and returns the normalized receipt `{status, operationId, kind, accountId, issuer, subject, sessionId, factorId, securityEpoch, requestFingerprint}` or a `not_found` result with null factor/epoch/fingerprint. It never returns envelope/code or mutates state. On an uncertain writer outcome the service makes one status lookup; if the receipt is missing or unavailable, return unknown and do not automatically retry a writer.

Migration 0014 currently contains these candidate declarations and a private append-only `factor_enrollment_operations` table. They remain unapplied; migration source and static tests do not prove PostgreSQL execution, locking, atomicity, or durability. The table uses `operation_id` as its primary key; stores account, issuer/subject, managed session, logical kind `begin|verify`, fixed-length keyed request fingerprint, factor/epoch, `pending|rejected|verified` status, and finite timestamps. Failed verification attempts use logical kind `verify`, not a separate receipt kind. The design excludes OTP, plaintext seed, key, provisioning URI, recovery code, and raw provider error. Migration 0014 grants no app access to lifecycle functions or tables; principal grants and live runtime acceptance remain separate gates.

## Receipt, retry, rate, and audit requirements

- Lifecycle receipts must be separate from 0012 `factor_challenge_operations`, whose check constraint only permits `attempt`, `totp`, and `recovery`. Store operation UUID, kind, account, issuer/subject, managed session, factor/epoch where applicable, outcome and finite timestamps. Never store the OTP, plaintext seed, envelope, key, provisioning URI, recovery code, or raw provider error.
- Same operation UUID is status-only after first invocation. Same-operation replay returns the original safe receipt; a different kind or binding returns unavailable. Unknown commit gets one read-only receipt lookup and no automatic writer retry.
- For begin and verify, the trusted service supplies an opaque `request_fingerprint` from an injected keyed-fingerprint port. The receipt stores only the fixed-length fingerprint and compares it on a reused operation ID; the six-digit code is never stored and an unkeyed hash is forbidden because it is brute-forceable. The offline contract can test the port boundary, but production key custody, rotation, and configuration remain a live prerequisite. No fingerprint key choice or provisioning is made here.
- Reuse the installed account-wide 5-attempt/15-minute enforcement semantics; the caller cannot raise limits or select another bucket. Count failed enrollment confirmations in the same protected account-wide window, including the failure audit outcome. Current 0012's public challenge reader requires a verified factor and cannot serve this pending-enrollment path as-is. The lifecycle migration must implement the pending-code failure accounting using the private existing window/audit tables or a reviewed fixed helper, preserving serialization and append-only history.
- Existing `privileged_factor_audit.outcome` permits `enrollment_started`, `enrollment_verified`, and `rate_limited`; its `reason` set permits `accepted`, `invalid`, `replay`, `expired`, `unavailable`, and `throttled`. Use only those existing values for this slice; do not broaden enums without a separate review. Record outcome/reason, actor/account, factor/epoch, and time—not submitted codes or cryptographic material.

## Locking and failure boundaries

1. Begin and verify first call the current `_factor_lock_identity` replacement installed by 0013, which locks the managed Auth session before account/identity. Its binding includes the exact issuer, subject, session ID, provider row expiry, active account, and owner/admin role. A caller-provided expiry cannot extend provider expiry.
2. Continue with epoch row, factor row, account serialization lock, and lifecycle operation/source row, preserving 0012 ordering. Establish one ordering for lifecycle-receipt and audit locks; no path may acquire them in reverse order.
3. Do not hold database locks while decrypting or evaluating TOTP. The service reads the pending envelope, decrypts/verifies outside the writer transaction, then calls the atomic verify function with the matched time-step candidate and trusted binding. The writer rereads and relocks everything before consuming the step.
4. Use finite server timestamps and `IS DISTINCT FROM`/null-closed checks. Deferred 0009 triggers must pass at commit: epoch event and epoch row agree; every factor insert/update references the current epoch; accepted step references the exact factor/account/epoch; the factor is pending before verification and verified by commit. Any raised error rolls back the complete lifecycle transaction.
5. The API returns verified only after commit plus a fresh post-commit identity/session/epoch/factor read. If that read fails, session expires, identity is revoked, or epoch changes, suppress success and protected data. Receipt recovery also performs the fresh binding check; a receipt is not itself current authorization.

## Blockers and next safe work

The offline protocol now calls the maintained factor storage and TOTP verifier contracts, with a synthetic interoperability check. That proves only local function compatibility. Runtime remains gated on execution/review of migration 0014, a dedicated credential and server-side key custody, production configuration for the keyed fingerprint port, a trusted caller boundary, and a real acceptance flow. Durable bootstrap seed-to-subject history is not established by this candidate and remains a separate prerequisite. No actual owner/admin fixture has been established, so no runtime MFA claim is possible.

The candidate service returns provisioning material only after a known committed begin and never from a status lookup. An uncertain begin can therefore leave a pending setup without returning the seed. The frozen source's one-time-code rule applies to recovery codes, not the TOTP provisioning QR. A later owner-authorized operation may be considered to redisplay the *same* encrypted pending seed without creating a new factor or advancing the epoch; this would require its own reviewed caller, audit, and session-binding contract. Cross-session recovery, pending cancellation, and expiry remain undecided and are not implemented here.

Next safe work after review: finish the parameterized repository adapter against the six exact candidate function signatures, then run the offline application and migration guards. Any later database execution or principal grant needs its own scoped acceptance gate. These checks validate only the application contract and static SQL shape, not database execution, locking, concurrency, or durability. Keep the candidate disconnected from routes, credentials, keys, SQL execution, grants, and privileged runtime.
