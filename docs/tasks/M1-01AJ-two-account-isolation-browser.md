# M1-01AJ — Same-environment account-isolation browser acceptance

Status: design only. This packet proposes a bounded acceptance plan; it creates no identity, account, session, record, route, fixture, or grant. It does not promote a requirement or replace any existing browser evidence.

## Authority and scope

Read `AGENTS.md`, `docs/STATE.md`, `docs/spec/15-shared-safeguards.md`, frozen Sections 11.3, 11.15, and 11.22(C–D), and the named views `docs/spec/00-overview.md`, `docs/spec/01-ui-nav.md`, `docs/spec/07-data-ops.md`, and `docs/spec/12-membership.md`. Relevant acceptance IDs are SYS-02, SYS-07, SYS-08, SYS-09, SYS-11, ACC-02, ACC-03, ACC-06, ACC-07, DATA-01, DATA-02, OP-01, OP-02, RULE-05, RULE-06, RULE-08, and FILE-10. The frozen source remains authoritative.

This slice tests same-environment ownership and account-switch clearing for the profile/records/import UI that currently exists. It is not complete SYS-02 acceptance for trips, chat, itineraries, tours, or monitoring; those surfaces still need their own owner-scoped live acceptance. It also cannot verify profile changes through intake, planner, or AI when those integrations are not wired.

## Current evidence and prerequisite

The prior single-account browser evidence uses its own recorded source revisions, including `15132077d1d244f3bdd1b042de4c11499d44fe37` for the baseline this packet reviewed. M1-01Z and M1-01AB records include single-account local browser acceptance, saved acknowledgments/reload, a selected-field import, sign-out clearing, and offline-validated transfer content. They do not prove two accounts in one environment, A→B→A switching, foreign-operation denial, or preview-vs-local account isolation. The exact source SHA for any future AJ run remains unpinned until a specific reviewed build is selected. M1-01Z's current helper is pinned to the existing `local-01` fixture and one sign-in code per run; it does not authorize a second account or a second send.

The available branch fixtures are one ordinary local account (`local-01`) and one ordinary preview account (`preview-01`). A second same-local ordinary member is not currently provisioned. M1-01AI has an offline synthetic-account provisioning candidate, but it remains unwired: it creates no fixture or account and is not a general member-provisioning path. None of its proposed owner/admin aliases may be repurposed for this test.

Before browser acceptance, separately review and approve a provider-supported, synthetic-only ordinary-member fixture in the local environment, with a distinct verified subject, role `member`, no privileged assignment, and no copied production identity. This fixture is a proposal and remains uncreated. Do not insert fake rows into provider auth tables, weaken migrations, reuse the preview identity, or use local-vs-preview as a substitute for two accounts on one environment. Any separate fixture-creation action and browser sign-in/capture needs its own action-time authorization. If no supported fixture path is approved, stop at this prerequisite and leave the live gate open.

## Preconditions for a later run

- Pin the exact reviewed source revision, local branch, issuer, loopback origin, and the two explicit synthetic fixture aliases in a bounded run record. The server derives identity/account; the browser never selects an account UUID.
- Keep scheduled and metered dispatch disabled. Use only the approved local test identities and manually authored synthetic marker values.
- Review a fixture-aware helper update. Preserve the current 30-minute maximum per admitted run, exact environment backup/restore, the current one-send/one-capture-per-run rule, no process restart after an admitted send, and failed-capture no-retry behavior. The current local-01-only helper cannot simply be invoked with an altered fixture selector. A second fixture requires its own exact run binding and action-time send/capture authorization; do not increase a run's send count implicitly.
- Use a same-origin browser context for each account. Do not print cookies, codes, private transport keys, raw provider errors, or account IDs. Capture only sanitized status, revisions, request IDs/hashes, and synthetic UI evidence.
- Before changing any existing data, record its canonical revision and the exact test-only field/record state. Never attempt a foreign-ID upsert, delete, removal, role, membership, or other destructive mutation under this plan.

## Acceptance sequence

1. **Account A baseline.** Sign in as the existing ordinary local synthetic account through the normal UI. Record only the canonical profile revision, non-sensitive counts, and synthetic test marker location. Save one disposable, clearly synthetic profile marker through the ordinary UI and wait for the durable Saved acknowledgment; reload and confirm its canonical value. Record one A-owned operation UUID for the owner-scoped status-read probe. Store no profile text or IDs in shared QA.
2. **Sign out and clear.** Use the ordinary sign-out control. Confirm protected profile/record controls disappear and the profile route requires sign-in. Confirm local application state and browser-visible cached profile content are cleared before another account's profile is shown. Do not treat an aborted request as proof that its server transaction rolled back.
3. **Account B baseline.** Sign in through the ordinary UI as the separately approved second local member. Confirm its own empty/default profile or its independently seeded B-only baseline. Confirm the A marker, A vehicle/note text, and A profile summary are absent from the rendered page, accessible text, and permitted application responses. Never send an account selector in the request.
4. **Foreign status/read boundary.** Using B's session only, request the documented operation-status URL for A's captured operation UUID. Expect the documented owner-safe unavailable/not-found outcome; confirm the response includes no A account ID, profile, revision, affected IDs, or saved payload. Record only status and a whitelist of response keys. If the API reveals any A data, stop and preserve evidence; do not continue.
5. **No foreign-ID write probe under the current contract.** Do not submit A's vehicle or note UUID in a B upsert. Migration 0005 keys these records by `(account_id, entity_id)`, so B can create a B-owned record with the same UUID without reading or changing A's record. That outcome is not, by itself, a cross-account access or ownership breach, and the current source does not define a foreign-ID write refusal. A B-only owner-scoped status read can show that B receives no A acknowledgment fields. If a valid A session is later available, compare A's canonical view before and after to check that this bounded run did not mutate A. These observations do not prove writer refusal or a general foreign-write boundary. Leave that broader proof open until a source-backed contract and suitable acceptance method exist. Do not issue a tombstone, delete, or value-changing cross-account write.
6. **Return to A (rapid A→B→A).** This requires another valid A session after signing out B. The current helper permits one send/capture per run, so do not request a second code or reuse a prior run. Only test this transition if separately approved, bounded run records can provide the needed sessions within the overall activation limit without restarting a process after an admitted send. Otherwise stop after the A→B observation and explicitly leave ACC-06 rapid-switch/cache acceptance open.
7. **Transfer/export boundary.** If included in the reviewed window, inspect B's native JSON/PDF only after normal preview and explicit opt-ins. Confirm neither includes A markers or records. Inspect local artifacts privately; retain only hashes, byte/page metadata, and sanitized pass/fail evidence. This proves only the tested export subset, not all formats or all data classes.
8. **Environment separation (separate assertion).** Use the existing `preview-01` only in a separately pinned preview run. Confirm local fixture/session credentials are not accepted on preview and the preview app reads only preview data; do not copy provider subjects, cookies, or database rows between branches. A successful local A/B test does not itself prove preview separation, and two different branch URLs do not prove same-environment account isolation.
9. **Cleanup.** Restore the exact prior local environment, stop only the owned server/process tree, verify the owned listener is gone, sign out, and retain sanitized run markers. Remove the disposable test marker only through the supported ordinary UI if that path is available and separately within the accepted run. Do not use SQL or provider-console deletion as cleanup.

## Evidence and stop rules

A successful run records the exact selected source SHA, run ID/expiry, fixture aliases by safe label only (A/B), environment binding, dispatch-off state, one-send/capture counts per approved identity, profile revisions before/after, owner-scoped operation-status classification, whether A's post-switch comparison was possible, A→B→A result, artifact hashes/metadata if tested, sign-out result, process cleanup, and exact failed checks. Record that foreign-ID write refusal remains untested under the current contract. Never include emails, subjects, account IDs, cookies, OTPs, private keys, profile values, or raw error/provider output in committed QA.

Stop immediately on an unexpected account/role mapping, stale or foreign content, a returned A field under B, an unexplained A revision/content change when A can be checked, an uncertain save, wrong environment, unexpected send/capture, provider fixture mismatch, expiry, or an owned-process cleanup failure. Preserve the draft and stop; do not retry with a new operation ID or expand the window. Confirm any accepted operation through its existing status/current-owner-profile flow.

## Acceptance boundary

This packet is a proposed test plan only. It does not create the second member, authorize provider actions, run a browser, or change the baseline helper. Even after the profile slice passes, SYS-02 / RULE-05 account isolation remains open for trip/chat/itinerary/tour/monitoring data and other browser contexts; ACC-06 remains open until its full cache and rapid-switch cases are observed. Preview separation, downloads, provider linking, full M1, and all requirement statuses remain independently governed by their source acceptance criteria.
