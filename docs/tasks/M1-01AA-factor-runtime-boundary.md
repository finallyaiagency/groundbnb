## Minimum future authority design

Keep factor access separate from the existing profile/membership connection. The prepared 0013 forward migration changes only the helper caller allowlist and creates the exact branch-specific principal in `NOLOGIN` mode. Any later authenticated runtime must use that same principal as `session_user`; a distinct LOGIN member or `SET ROLE` does not satisfy the caller check. A separately reviewed action may enable `LOGIN` and provision credentials on that same principal after confirming Neon role and credential behavior in the exact target environment. Every runtime principal must be non-superuser, non-createdb, non-createrole, non-replication, non-bypass-RLS, non-inheriting, and have a small connection limit. The principal needs only database CONNECT, schema USAGE, and EXECUTE on the five exact 0012 entry points. It must receive no table, sequence, helper, profile, membership, or general schema write grants. Revoke PUBLIC rights as appropriate and verify effective privileges with `has_function_privilege`, `has_table_privilege`, and `has_sequence_privilege` after each change.

Never grant these functions to either ordinary app role, a shared owner role, `PUBLIC`, or a broad runtime role. A dedicated credential must be usable only by server-side factor code. Keep the factor URL out of client bundles, browser-readable configuration, logs, diagnostics, source control, and ordinary profile persistence. Do not add a role-membership path that lets the ordinary app role `SET ROLE` to the factor principal. Local and preview principals and URLs must be distinct and pinned to their respective branch. Production and recovery are outside this task.

The deployment boundary is still an explicit design choice: a project-level server secret is available to all server code in that deployment, so a module name or `server-only` import alone does not isolate it from other server routes. Either treat the complete trusted server deployment as inside the factor credential/key boundary and review dependencies accordingly, or design a separate internal factor runtime with authenticated service-to-service calls. Do not imply per-route secret isolation unless the selected platform configuration actually enforces it.

The key provider must be a separate server-only dependency from the database principal. Use the existing AES-256-GCM/context-bound envelope and `keyId` contract; do not implement cryptography. A future decision must select the actual secret manager and document per-environment key generation, identifier/versioning, rotation with old-key decryption during migration, backup/recovery, and retirement. Keys must be separate from database/auth/recovery credentials and absent from SQL, repository files, client responses, logs, and AI context. Until that provider and rotation/recovery design are reviewed and the external key is provisioned through an approved secure path, factor reads/challenges fail closed. No key is generated or placed by this packet.

The server context must come from a fresh managed-session read and the pinned environment issuer, then bind the session ID and expiry against the same database's `neon_auth.session` row. Recheck expiry, account mapping, active status/role, factor ID, security epoch, rate state, and provider session state under the SQL function's established lock order. Do not trust request account IDs, role/email claims, factor state, freshness, or timestamps. A successful consume is returned only after commit and a fresh identity/policy read; uncertain commits receive one exact owner/session/method-bound receipt lookup and no automatic retry. Protected reads need closed resource-specific operations that recheck the same policy; no generic SQL or arbitrary callback.
