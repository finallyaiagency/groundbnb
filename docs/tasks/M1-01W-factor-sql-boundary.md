# M1-01W — Candidate private factor SQL boundary

**Status: In progress — design candidate for parent review.** No SQL, grants, routes, key activation, or live MFA are implemented or authorized by this document.

## Authority and prerequisite state

This design follows frozen Section 11.22(D), ACC-08, ACC-09, ADM-01, ADM-06, SYS-07, and `docs/spec/15-shared-safeguards.md`. It is subordinate to `docs/tasks/M1-01V-factor-repository-adapter.md`; it does not amend the frozen source. The current pinned synthetic baseline has migrations 0001–0009. Migrations 0010–0011 are outside the prior 0003–0009 approval and must be applied/approved before a factor-function migration can rely on their recovery-attestation and activity objects. The app roles have no factor-table privileges. No candidate below exists in SQL today.

The candidate requires a separate exact-database migration approval, a separate narrow function-EXECUTE grant approval, and later synthetic runtime acceptance. Do not wire the adapter to any environment until those gates pass.

## Function signatures and adapter results

These five signatures match the current fixed calls in `lib/factor-postgres-repository.mjs`. Each returns one JSONB value named `result`. Callers supply the SDK-validated session expiry and observed factor/epoch only for revalidation; SQL independently derives current ownership and security state. There are no caller-selected account IDs, roles, persistence timestamps, candidate digests or rate decisions. All signatures are candidates pending review.

| Candidate function | Exact PostgreSQL signature | Successful result contract |
| --- | --- | --- |
| `read_factor_challenge_state` | `(text issuer, text subject, text session_id, timestamptz session_expires_at) RETURNS jsonb` | Closed state: `principal(accountId,issuer,subject,sessionId,accountStatus,role,securityEpoch)`, `currentSecurityEpoch`, `accountSuspended`, `sessionRevoked`, `rateLimited`, `factor(accountId,factorId,securityEpoch,state,keyId,envelope,lastAcceptedStep)`, and at most 100 `recoveryRecords(recoveryId,accountId,factorId,securityEpoch,record(version,salt,digest))`. Internal-only; never return to a client or log. |
| `record_factor_challenge_attempt` | `(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid factor_id, bigint security_epoch, uuid operation_id, text method, text outcome, integer max_failures, integer window_seconds) RETURNS jsonb` | Exactly `{"status":"recorded"}` after its rate update, audit, and immutable receipt commit; failure/unknown at the adapter boundary is `unknown`. `method` is `totp` or `recovery`; `outcome` is `rejected` or `unavailable`. |
| `consume_factor_totp_candidate` | `(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid factor_id, bigint security_epoch, bigint matched_step, uuid operation_id, integer max_failures, integer window_seconds) RETURNS jsonb` | Exactly `{"status":"accepted"}` or `{"status":"rejected"}` after commit. A transport/commit uncertainty remains `unknown` in the adapter and is resolved only by receipt lookup. |
| `consume_factor_recovery_candidate` | `(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid factor_id, bigint security_epoch, uuid recovery_id, uuid operation_id, integer max_failures, integer window_seconds) RETURNS jsonb` | Same result enum as TOTP; a recovery source is consumed once and yields a recovery attestation without fabricating a TOTP step. |
| `read_factor_operation_receipt` | `(text issuer, text subject, text session_id, timestamptz session_expires_at, uuid operation_id, text method) RETURNS jsonb` | Exact keys `status,operationId,method,accountId,issuer,subject,sessionId`; status is `accepted`, `rejected`, `unavailable`, or `not_found`. Malformed arguments, inactive/revoked mappings, wrong role/status/epoch/factor, or stale challenges fail closed. SQL exceptions do not become success-shaped JSON. The adapter suppresses SQL/driver details and converts writer errors to `unknown`; it must never retry a writer. A post-commit receipt read is read-only.

## Owner, session, factor, and transaction rules

The reader and every writer must bind the SDK result to the same-database Neon Auth session row, then derive the Groundbnb account from its verified subject and current `account_identities`/`accounts` rows. Read only the session's `id`, `userId`, and `expiresAt`; never select or return its `token`. Require the environment-pinned issuer, session `id` equal to the resolved managed session ID, `userId` equal to the verified subject, a positive effective expiry no later than either the provider-row expiry or the SDK-validated expiry (compare exact instants; never extend an expiry), and a finite future row expiry checked with `clock_timestamp()`. Then require the unrevoked app identity mapping, active account, role `owner` or `admin`, current `account_security_epochs` row, current verified enrollment, matching factor ID/epoch, and no active rate block. Return suspended/revoked booleans only as fixed server facts; never accept them from the adapter. Recovery rows are selected for that same account/factor/epoch and only while unconsumed, with a hard SQL limit of 100 and deterministic ordering.

The read-only local catalog inspection confirmed `neon_auth.session` has `id uuid`, `expiresAt timestamptz`, `token text`, timestamps, `userId uuid`, and optional metadata columns; no session row values were read. The candidate predicate should compare `session.id::text` and `session.userId::text` to the SDK-bound identifiers and compare the stored expiry to the SDK expiry after native PostgreSQL timestamp conversion. The future function's definer must have only the narrow internal read it needs; app roles retain no direct `neon_auth` privileges.

Use one canonical lock order for all mutating functions: lock the exact `neon_auth.session` row first; resolve and lock the app account/identity rows; lock the account security-epoch row; lock the verified factor row; lock the account-wide rate bucket/window; lock or inspect the operation receipt; then lock the selected TOTP-step or recovery row; finally insert the attestation, immutable receipt, and audit. Ensure all conflict/`ON CONFLICT` and replay paths obey this order. Re-read the session row, ownership, active role/status, identity revocation, current epoch, factor state, expiry, rate state, and source usability under those locks before any write. Use database time for windows and challenge freshness. If revocation deletes the session row, a revocation racing a writer is ordered by whichever transaction locks/deletes that row first; confirm the provider actually uses that lifecycle and does not revoke through an out-of-band cache or separate store before treating this as a guarantee. Check for lock-order interaction with Neon Auth operations before finalizing the order.

TOTP consume also requires `matched_step` within the verifier's current ±1 thirty-second step and newer than every accepted step for this factor/epoch. Uniqueness on accepted step prevents concurrent reuse. Recovery consume locks the exact recovery row and requires matching owner/factor/epoch plus `consumed_at IS NULL`. The source, attestation, operation receipt, audit, and rate changes commit atomically. The 0010 source trigger requires `factor_verified_at` to equal the consumed source timestamp; use the database `accepted_at` or `consumed_at`, never a fabricated application timestamp. Challenge expiration must not exceed session expiry or the 12-hour factor freshness window.

For an operation UUID already present, compare its derived account, issuer, subject, session, and method before returning its immutable original result. Same-operation replay returns that original receipt; a different operation cannot reuse the source. Do not overwrite an original acknowledgment with later status. Keep operation kind/outcome internal to the receipt schema if needed to distinguish an attempt audit from a successful consume; expose only the fixed response contract above. Operation IDs are idempotency handles, not credentials.

## Rate accounting and audit

Migrations 0009 provide `factor_attempt_windows` and append-only `privileged_factor_audit`. The function must not accept raw token/code, secret, cookie, raw client IP, or an application timestamp. Attempt recording uses database time, increments once per unique operation, and appends a bounded audit in the same transaction. Rate-limited submissions are audited without resetting or shortening a window. Invalid, unavailable-key, and throttled outcomes are closed enums only.

Parent implementation choice for the future synthetic slice is `maxFailures=5` and `windowSeconds=900`; the frozen source requires limiting without prescribing these numbers. This is a routine implementation choice, not an amendment or active production policy. SQL must reject any parameter values differing from this fixed policy. Use UTC-aligned 15-minute windows and one account-wide total across all identity aliases and both challenge methods. The current 0009 key includes account, issuer, subject and bucket fingerprint: sum failures for the derived account/current window across every identity, while retaining exact identity provenance in individual rows. A fixed server-derived bucket fingerprint cannot vary by session, IP or submitted credential. Serialize all insert/update/admission paths under the account lock and preserve 0009 non-overlap/monotonic-window guards. Test alias switching, method switching, boundary resets, concurrency and rejected caller overrides before any live claim.

## Session-revocation capability and proof still required

The server identity resolver uses the SDK's uncached `getSession({ query: { disableCookieCache: 'true' } })` path and returns the session ID and validated expiry. The new catalog metadata shows a same-database `neon_auth.session` candidate with the necessary `id`, `userId`, and `expiresAt` columns. A narrowly scoped SECURITY DEFINER can potentially bind that exact row to the verified user and lock it before any factor write. This is a design candidate, not evidence that deleting/revoking a session uses that row or that the SDK and SQL observe revocation with the required consistency.

Before claiming revocation enforcement, inspect the installed Neon Auth SDK/source and official provider documentation for the uncached-read behavior, session deletion/revocation lifecycle, replication/cache guarantees, and whether a revoked session is immediately absent or otherwise marked in this row. Then use a bounded genuine synthetic acceptance test to revoke/delete one managed session through the supported provider path and verify: a fresh SDK read fails; the same-database factor reader/writer denies it; a writer concurrent with revocation has only the documented lock-order outcome; and neither interface reads or returns the session token. Do not read session values for this design or grant app table access to run these checks. Until those semantics and regression evidence exist, retain the limitation that provider-side revocation behavior and cross-operation ordering are unknown; post-write SDK resolution may withhold access but cannot undo a consumed factor source.

## Receipt table and migration safety

The candidate migration needs a private receipt table keyed by operation UUID, with derived account and exact issuer/subject/session/method binding, internal operation kind, closed result status, and database creation time. Enforce immutability; allow only one initial insert by the new writer functions. Store no token, recovery code, secret, ciphertext, digest, or unsalted credential fingerprint. A receipt status read must return `not_found` for a foreign binding without exposing whether another owner has that UUID. Preserve the original status forever; no update-based acknowledgment replacement.

The future forward migration must pin database `groundbnb`, exact local or preview branch, complete approved migration receipts, sole verified synthetic identity, and the exact existing app-role function-only/table-denied ACL baseline. Functions must be narrowly scoped `SECURITY DEFINER` with `search_path=pg_catalog,pg_temp`; revoke default `PUBLIC` execute and grant only the five intended signatures to the environment's app role after a separate grant decision. Keep helpers and receipt/table access private. Never run an adapter against an absent function.

The reverse migration must refuse rollback if any factor enrollment, recovery row, accepted step, attestation, attempt window, factor audit, security-epoch event, privileged activity, or operation receipt exists. It may remove only the newly introduced empty receipt object and newly introduced functions/helpers; it must preserve all existing 0009/0010 history. Do not make migration or grant changes until ordering and approval are explicit.

## Requirement mapping and remaining evidence

- **ACC-08 / ACC-09, ADM-01 / ADM-06:** trusted managed identity, second-factor challenge, owner/session binding, one-use source, rate control, audit, and step-up dependencies. The candidate functions do not implement enrollment, reset, privileged resource reads, or browser enforcement.
- **SYS-07:** owner-authorized closed mutations with durable original receipts; live transaction and acknowledgment behavior remain unproven.
- **SYS-11:** dormant, isolated, function-only access and no direct factor-table privileges; runtime branch/session isolation needs revalidation as integrations are enabled.
- **M1-01V:** fixed parameter order/results, one-call writers, receipt reconciliation, no blind retry, current identity/factor checks, key/storage separation, and distinct migration/grant/runtime gates.

Still open: final function contract review; 0010/0011 ordering and approval; implementation and proof of the selected account-wide rate policy; exact managed-session revocation capability; DB function/trigger compile and operator checks; effective ACL readback; concurrency/one-use/unknown-commit runtime tests; and eventual browser/service acceptance. The adapter and mock tests prove none of those database or live MFA properties.
