## Window helper

Use `scripts/m1-browser-acceptance-window.ps1` for the already authorized bounded local continuation. `Prepare` creates a GUID-named run directory under ignored `.tmp/evidence/m1-browser-runs`, saves the current local environment in a unique CurrentUser-DPAPI backup, and writes a run record plus a DPAPI-protected hash. It pins the existing local app binding, `local-01@example.test`, local branch, local issuer, localhost origin, full-v1 profile mode, 30-minute maximum, capture email, and disabled scheduled/metered work. It does not request an OTP. Prior M1-01E attempt metadata and send/diagnostic markers are left in place; no old expiry or history is rewritten.

`AdmitSend -RunId <id>` creates one exclusive send-admission marker. The operator then sends exactly one code through the ordinary UI. The helper itself does not call the provider or browser. Never resend, reload the sign-in form to request another code, or admit a diagnostic send after a failure. The route rejects a second send for the same synthetic run while that server process remains alive. This counter is process-local; do not restart the app after admitting a send. It is not a distributed or restart-proof limiter.

`Prepare` copies the existing public transport key into the unique run directory. `Capture -RunId <id>` is admissible once after send admission and before expiry. It reuses only the existing DPAPI-protected local capture inbox, invokes the existing bounded read-only capture helper with the exact per-run encrypted-output path, and suppresses code/credentials/errors. The existing matching private-key handling remains the operator's responsibility. A failed or uncertain capture consumes the capture attempt; preserve the run and do not retry against the inbox without a new approved window. The helper's legacy default output remains available for the earlier workflow and is not overwritten by this run.

`Close -RunId <id>` requires that the active `.env.development.local` run ID matches, restores the exact protected backup, records a close marker, and removes only that run's consumed encrypted backup. Run records, send/capture/close markers, and encrypted OTP evidence are retained. Expiry is fixed in the protected run record; helper actions cannot extend it. Close is permitted after expiry.

Only the existing synthetic local fixture is in scope. No preview, production, recovery, identity creation, password change, second account, role/admin action, MFA claim, or metered dispatch is authorized by this packet. Existing membership migration/grant or provider-factor work is separate.

## Local production proxy plan

The prior attempt already proved sign-in/profile save/conflict/reload in one tab pair, but did not prove response-loss replay. The previous response-loss proxy's offline tests pass. Its real-browser run never dropped a committed save: Next development output did not hydrate through the proxy, then production access yielded `ERR_BLOCKED_BY_CLIENT` through the proxy and a timeout after direct server replacement. HMR was a hypothesis, not an established cause; logout was not confirmed. Do not repeat those results as a replay or revocation pass.

For a new replay attempt, use a local production build and start the Next server on `127.0.0.1:3001`; run the response-loss proxy on `127.0.0.1:3000`; keep the browser at exactly `http://localhost:3000`. Load `.env.development.local` with Node's `process.loadEnvFile` in a private parent launcher and pass that environment to the build/start child process. Do not pass Node `--env-file` through Next's worker. Production `next start` removes the development HMR dependency.

The proxy must make only local upstream calls to port 3001. Preserve browser `Origin` and `Cookie` on forwarded requests, and forward host-only `Set-Cookie` responses without adding a `Domain`; the browser therefore retains the same `localhost:3000` origin and cookie jar. The proxy forwards same-origin headers and streams non-API assets while applying bounded buffers to API bodies. `--run-record` accepts only the exact `.tmp/evidence/m1-browser-runs/<runId>/run.json` path, requires the run's integrity sidecar to exist, and enforces the fixed run ID/fixture/full-v1 mode/one-OTP/window fields. The legacy fixed M1-01E path remains unchanged. The Node proxy checks path and record bounds but does not verify the DPAPI-protected hash; do not treat that proxy check as a tamper-proof integrity check. The PowerShell window helper verifies the DPAPI hash when it admits or captures an action. During the bounded local response-loss attempt, the proxy may emit a fixed-field status-recovery result for one canonical `GET /api/account/profile/operations/<operationId>` matching the dropped operation. It compares operation/account hashes, revision, and savedAt internally; raw account identifiers are never emitted. Do not overwrite historical attempt evidence.

For the response-loss gate, the operator submits one normal profile PATCH. The proxy consumes the first successful 200 response and drops the browser connection once; it does not repeat or delay the provider/application request. The UI must show an uncertain save and retain the original operation ID/revision. The required next action is a status read. If status says `saved`, the UI adopts that owned acknowledgment and transitions to Saved without another PATCH. The status acknowledgment must match the original operation ID, account binding, revision, and savedAt. If status says `not_found`, that observation does not prove an in-flight write cannot commit; only then may the user explicitly retry with the same operation ID/revision. Never automatically repeat a write. A proxy event or synthetic test alone is not a pass. Any mismatch or unknown result preserves the original operation and blocks a blind retry.

The historical browser attempt dropped a committed profile response at revision 4; the subsequent status read found it saved, and the UI recovered to Saved without a PATCH replay. That is correct committed-status recovery. It does not establish that a true explicit PATCH replay occurred; record the status-recovery evidence separately and keep explicit write-replay evidence open unless observed in a separate permitted not-found path.

After the profile check, logout acceptance requires the app cookie cleared and a fresh managed-session check to show absence. If the local browser/proxy fails, close the window, retain all attempt markers and report the failing phase/category without retrying. No M1 exit or M2 handoff follows from this local slice alone.
