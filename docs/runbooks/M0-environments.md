# M0 environment and recovery runbook

This is a configuration contract, not evidence of a live branch, auth service, or restore drill. Record IDs and dated console observations in `docs/qa/` after provisioning. Never place connection strings, auth tokens, email addresses of real users, or HMAC keys in Git or task context.

1. Keep the existing `groundbnb` production branch and named database. Set `GROUND_ENV=production`, its pinned branch/endpoint, production-only auth issuer, cookie name, callback origin, and production-only credentials in Vercel Production variables. Reject an environment if `GET /api/health` is not `configuration_valid` with the expected revision. This checks configuration shape only; verify database connectivity and branch identity separately.
2. Create a separate empty/schema-only or synthetic template branch. Confirm both application tables and `neon_auth` identities/sessions are empty before using it as a preview/local parent. A normal data branch copies data and auth; do not enable automatic production-to-preview branching. Give preview and local separate branch IDs, endpoints, credentials, auth issuers, cookie names, OAuth callback origins, and email capture. Restrict preview access to owner/developers with Vercel Deployment Protection. Set scheduled work and paid dispatch `off` by default. Never use real bootstrap emails for seeds.
3. Apply `db/migrations/0001_environment.sql` on each empty product branch in a SQL transaction, then insert the exact environment kind and branch ID into `groundbnb.environment_identity`. Verify one matching row and `schema_migrations`, then test synthetic seed refusal on production and acceptance only on preview/local. Check the branch identity before each subsequent migration; stop if absent or mismatched. The down script is destructive and is only for an isolated disposable test branch. For production rollback, restore an approved prior deployment or forward-fix after assessing data changes.
4. Create a separate, access-restricted recovery-control database/branch whose lifecycle is outside the production restore target. Apply `db/recovery/0001_controls.sql`; store its HMAC key outside production snapshots and Git. Inventory all recoverable snapshots and manual backups. Retain deletion/revocation controls until the last capable restore point expires plus seven days. Set Neon recovery retention to at least seven days if the project plan permits; record actual window/granularity and the last recoverable time. The four-hour recovery-time target remains unproven until a timed drill.
5. Restore into a quarantined branch with login, workers, email, and paid dispatch off. Refuse reopening if the recovery ledger or key is unavailable. Replay deletion/revocation epochs, purge restored deleted content, invalidate pre-restore sessions/agent credentials, verify roles/bootstrap revocations, then enable service. Drill with one deleted synthetic account, one revoked session/credential, and one revoked seed administrator. Preserve timings and results without personal data.
6. A preview live test requires an explicit run ID, approved synthetic accounts/recipients, a start and expiry no more than 60 minutes apart, and at most 0.25 USD aggregate provider budget by default. `validateEnvironment` checks this envelope; any future dispatcher must make an atomic durable reservation before every call and reject use after expiry. A retry cannot extend the window. Delete obsolete preview resources within seven days after PR closure, after retaining redacted evidence.

The M0 operator must confirm preview branches contain zero production identities, records, sessions, and secrets; verify Vercel branch-scoped variables and deployment protection; then record actual branch/deployment IDs and a bounded rollback observation. The holding page has no product auth or metered integration yet, so these live pass conditions remain open.
